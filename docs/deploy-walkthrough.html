If you pick B, GitHub's uploader keeps folder structure when you drag a whole folder, but do it in one go rather than folder by folder — partial uploads across several commits get messy.

PHASE 2

Stand up the database on Railway

3

Sign in to Railway YOU

Go to railway.app and sign in with GitHub. Using the same GitHub account means Railway can see the repository without any extra connecting step.

Railway needs a payment method on file before it will run a database beyond the trial. That's yours to decide and yours to enter — I won't touch billing pages even with browser access.
4

Create the project YOU

New Project → Deploy from GitHub repo → pick burkina-training-log.

Railway will try to detect an application to build and won't find one, because there isn't a server yet — only the schema and the docs. That's expected. The deploy will fail or sit idle and it doesn't matter; the database is what we're here for.

5

Add Postgres — and stop at the region YOU

Inside the project: New → Database → Add PostgreSQL.

STOP HERE

Railway asks which region to put it in. The choices are US West, US East, EU West (Amsterdam) and Southeast Asia. There is no Africa region.

If the in-country data position Sunil took on Selltis — infrastructure handled off-site and strictly in Burkina Faso or countries where the product is deployed — applies to this programme too, then Railway cannot satisfy it at all, and what you're building here is a pilot with no real instructor or learner data in it.

If it doesn't apply, EU West (Amsterdam) is the sensible pick: closest of the four to Ouagadougou, so the least latency for people syncing over a poor connection.

Either way this is worth a two-line email to Sunil before you click, not after.

6

Find the connection string YOU

Click the Postgres service → Variables tab → copy DATABASE_PUBLIC_URL.

There are two similar variables. DATABASE_URL only works from inside Railway's own network. DATABASE_PUBLIC_URL is the one reachable from outside, which is what's needed to load the schema from here.

It looks like postgresql://postgres:…@…proxy.rlwy.net:12345/railway.

This is a password. Anyone holding it has full access to the database. Once the schema is loaded you can rotate it from Railway — and while the database holds nothing but reference data, the exposure is close to meaningless. It stops being meaningless the moment real instructor data goes in.
7

Load the schema and seed data CLAUDE

Give me that connection string and I'll run the four files in order, then the constraint tests, and show you the result. Takes a few seconds.

db/schema.sql db/seed/01-reference.sql db/seed/02-curriculum.sql db/demo/demo-data.sql

You should see 4 tracks, 25 modules, 83 lessons and 92 objectives land, then eight constraint tests pass.

If you'd rather not hand over the string: Railway's dashboard has a query window under the Postgres service's Data tab. You can paste each file's contents in yourself, in that order. It works, it's just tedious — the schema file is around 700 lines.

10

The decisions this doesn't settle YOU

Standing the database up doesn't answer any of these, and two of them get more expensive the longer they wait:

  • Data residency — the Sunil question in step 5.
  • Curriculum stability — if the lesson list is still moving, the add-and-retire approach may not be enough and versioning is much cheaper to do now than later.
  • Parallel or sequential tracks — the model assumes a cohort does one track. If everyone actually does CS foundations first and then branches, the lesson codes and the progress arithmetic both change.
  • Objective wording — too many still say "explain X" rather than "build X". The demonstration rate measures exactly those objectives, so a weak objective produces a confident number about nothing.
  • French technical vocabulary — needs an instructor in-country to read it before it goes near a class.

All five are written up in docs/open-decisions.md.
